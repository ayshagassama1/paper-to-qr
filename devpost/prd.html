Product requirements Draft

Paper to QR

A photo of a paper or chalkboard menu becomes an editable digital menu, a code and a printable QR code. For the manager whose menu of the day changes often, and the customers who scan it at the table.

What scope said, what we know now

"The manager opens the site"
→
A Uxcel-style hero: logo, H1, subtext, and two buttons that open tabs. Existing menu is open by default.
"OCR extracts the list"
→
The screen shows the current step in plain English, not a percentage that could mislead.
"Edit or delete dishes"
→
The line becomes editable in place, the pencil turns into a check. Plus Add dish and an active/inactive toggle.
"Add a dish? New photo?" (open)
→
Add dish is in. Re-uploading a photo is deferred.

→
The restaurant name and the active dishes with prices. Nothing else.

Aim for

Simple, clean, readable, and cosy. What Uber and Instagram get right: you see what the platform offers at first glance, there isn't much text but it's understandable, there is a balance. UI in English.

Avoid
  • emoji
  • em dashes
  • chalkboard imagery
  • purple AI gradients
  • nav links
  • title top, icons bottom, hamburger top left

Product decisions

Tabs, not pagesThe hero buttons open tabs; navigation links serve no purpose here.
Existing menu by defaultThe returning manager is the frequent visitor.
One Menu screen for both pathsSame screen after a code or after processing.
Name is read-onlyThe QR code's URL is built from it.
Edit in place, validate with a checkThe pencil becomes a check.
Steps, not a percentageProcessing time is unknown; a bar could mislead.
Add dish + active toggleThe menu of the day changes and dishes run out. Add dish also covers "nothing extracted".
Fraunces + DM Sans, English UIMore distinctive than Montserrat; judges read English.

Assumptions to confirm

  • The restaurant, code and QR are created as soon as processing finishes, even with no dish found.
  • Deleting a dish is immediate, no confirmation.
  • A dish needs a name to be validated.
  • Two restaurants with the same name get different URLs.
  • The code is short and easy to copy; its format is set in the spec.
  • Unknown slug: "Restaurant not found" page. No active dish: name plus "No dishes available right now".

Boundary

What we're building 8
  • Home screen: logo, H1, subtext, two tab buttons
  • Existing menu: find by code, error on unknown code
  • New restaurant: name, one or more photos, step-based status
  • Extraction of dishes and prices from the photos
  • Menu screen: read-only name, inline edit, delete, add, active toggle, QR download, code
  • Fallback when nothing is extracted: message plus manual entry
  • Customer page /restaurant-slug: name and active dishes
  • Deployed for the judges
Deferred from the POC 3
  • Replacing the menu with a new photo: Add dish covers daily changes for now.
  • Recovering a lost code: would need an email or account, against the kernel.
  • Renaming a restaurant: would break printed QR codes.
Later enhancements 3
  • Customizing the customer page (colors, logo)
  • Categories, descriptions, allergens
  • Re-uploading a photo to replace or extend the menu
Non-goals 4
  • Accounts and authentication: the code is the only key
  • Storing uploaded photos
  • Navigation links in the navbar
  • Anything on the customer page beyond name and active dishes
