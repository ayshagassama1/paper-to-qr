Paper to QR

How the approved PRD gets built: React on S3 and CloudFront, FastAPI on Lambda, Claude Haiku 5.5 reading the photos, and one MongoDB collection.

How it works, in plain language

The website

React

Everything people see. Shrinks photos before sending (and strips their metadata). Draws the QR code itself.

The API

FastAPI on Lambda

Wakes up on request. Creates restaurants, finds a menu by code, saves dish changes.

The reader

Claude Haiku 5.5

Gets the photos, returns dishes and prices as validated JSON. Well under a cent per menu.

The memory

MongoDB Atlas

One restaurants collection: name, slug, code, dishes. Nothing else.

Chez Marcel's manager photographs the chalkboard. The browser shrinks it and sends it with the name. The API asks Claude for the dishes, saves Chez Marcel with a new code and the slug chez-marcel, and sends it all back. The browser shows the list, the code, and a QR code for /chez-marcel. Next day, the code finds the same document, and every click updates it. A customer scanning the QR code sees the active dishes.

The manager comes back

GET /api/manage with the code header. 404 shows "Restaurant not found" on the form; 200 opens the same MenuEditor. The code is case-insensitive, dash optional.

API

EndpointSendGet back
POST /api/restaurantsmultipart: name, 1 to 5 images201 RestaurantPrivate (with extraction_empty)
GET /api/manageheader X-Menu-Code200 RestaurantPrivate, or 404 "Restaurant not found"
POST /api/manage/dishescode header; {name, price_cents}201 Dish (422 if name blank)
PATCH /api/manage/dishes/{id}code header; any of name, price_cents, active200 Dish
DELETE /api/manage/dishes/{id}code header204
GET /api/menus/{slug}nothing200 name + active dishes, or 404

The code travels in a header, not the URL, so it stays out of CloudFront and API Gateway access logs.

Look and feel, as code

Cards: white page; cards filled with #E9F2F3 with a 1 px #D0E0E2 hairline, one tone darker than the fill, as on Uxcel. Used sparingly: text sits on the page, not in boxes. No shadow. Inputs and the QR code sit on white inside cards.

Contrast, checked against WCAG AA

ink on white 15.3 · ink-soft on surface 5.5 · white on petrol 6.9 · petrol on surface 6.1 · apricot-ink on apricot 7.5. All text pairs pass 4.5:1. --border (1.4:1) is fine for dividers but too faint for input outlines, hence --input-border.

Where it breaks, and what people see

Claude can't read the photo, refuses, or errors
→
Restaurant still created; "clearer photo or add your dishes below" with an empty list
Extraction over about 29 s
→
"Reading your menu took too long. Try again with fewer photos." Nothing created.
Browser can't decode the photo (HEIC in Chrome)
→
"This image format isn't supported. Try a JPEG or PNG photo." before upload
Unknown code or slug
→
"Restaurant not found" on the form or the page

Running it

Locally
  • backend/.env from .env.example: MONGODB_URI, MONGODB_DB, ANTHROPIC_API_KEY (never committed)
  • uvicorn app.main:app --reload --port 8000 in backend/
  • npm run dev -- --host in frontend/ (Vite proxies /api)
  • Open the LAN address Vite prints: the QR code uses window.location.origin, so a phone on the same Wi-Fi can scan it.
Deployed with SAM
  • sam build && sam deploy --guided: Lambda (Python 3.12, 512 MB, 29 s), HTTP API, private S3 + OAC, CloudFront, CloudFront Function for the SPA fallback. Keys as NoEcho parameters.
  • npm run build, aws s3 sync dist s3://<bucket> --delete, then a CloudFront invalidation.
  • No CloudFront custom error pages for the fallback: they would turn the API's 404 into index.html.
  • Atlas open to 0.0.0.0/0 (Lambda outside a VPC has no fixed IP).
  • Verify early: Lambda's ~6 MB payload, the HTTP API's ~30 s timeout, base64 inflation (~+33%).

Simplified on purpose 6
  • QR drawn in the browser, not stored: it's fully determined by the URL.
  • One Lambda for the whole API.
  • One request per menu, no job queue or polling; the steps stay honest without streaming.
  • Code stored in plain text, not hashed; low-stakes, easy to add later.
  • Atlas open to all IPs instead of VPC peering; throwaway data.
  • No manager session: the code is typed again, as the kernel intends.
